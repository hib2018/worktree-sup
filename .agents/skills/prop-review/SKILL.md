# prop-review: request to reviewable proposals

Start from the human's own words. Write proposal text and the human-facing handoff in the language of the human's request, even when repository docs, CLI UI, or skill instructions use English. On revision, preserve the original request language even if comments use another language. This is a lightweight discussion, not an approval gate for a whole project. Use it for early ideas and direction-setting, but also for other requests when the human wants to review possible choices or next steps. Do not turn a request for facts only or direct implementation into an approval session without being asked.

1. If the request lacks the minimum context to propose anything concrete, ask one short question. Otherwise write up to 10 small, independently reviewable items (around 10 when warranted; fewer rather than padding). Inspect the relevant project when proposals depend on its actual state. Convert findings into specific proposed responses rather than asking the human to approve a fact; distinguish confirmed problems from optional improvements. Make assumptions explicit in each item; do not invent requirements or silently expand scope.
2. When the human wants CLI generation, ask them to run `prop-review generate` in the repository; it asks `Request:`, invokes the user-selected engine (Pi or fx, default Pi) to read the repository, creates a new proposal and starts review. For GitHub issues, ask them to run `prop-review issue` in the repository: it lists open issues via `gh`, asks for a listed issue number, generates proposals and starts review. Only Pi and fx are supported. The human can switch the user-wide engine beforehand with `prop-review --engine pi` or `prop-review --engine fx`. Pi generation uses a read-only SDK session with extensions, skills, and prompt templates disabled, not the `pi` CLI. fx generation uses `fx ask --no-save --json` and reads only the JSON response's `final_output`, never accumulated output; instructions alone do not enforce fx tool permissions. An existing invalid saved engine setting must be explicitly replaced with `prop-review --engine pi` or `prop-review --engine fx`; never silently fall back. Pi is the default only when no setting exists. Do not run the interactive CLI on the human's behalf. For manually drafted items, find the repository root with `git rev-parse --show-toplevel`. Create `<repo-root>/prop-review-tmp/`, keep it out of Git by adding `/prop-review-tmp/` to that repository's local `info/exclude` (`git rev-parse --git-path info/exclude`) if not already ignored. Never delete earlier `review.*` directories. Create a unique directory with `mktemp -d <repo-root>/prop-review-tmp/review.XXXXXX` and write `proposal.txt` there (blank approval lines, no other headings). `Approval/Comment:` is a fixed file-format token, not prose to translate; leave it empty in proposals. If there is no repository, ask where to save:

   ```text
   <one concrete proposal>
   Approval/Comment:

   <another proposal>
   Approval/Comment:
   ```

3. For manually drafted items, show them to the human and give the command `prop-review` to run from anywhere inside that repository. It opens the only unreviewed proposal under `prop-review-tmp/`, or lists unreviewed proposals for the human to select when several exist (newest modification time, then path). The human can also run `prop-review <proposal.txt>` to select one directly. By default the result is saved beside the proposal as `proposal.review.txt`. Reviewing alone does not add a Git exclusion; ensure manually drafted proposals are ignored as described above. Proposals and results remain on disk until explicitly deleted; they are not promoted to durable project artifacts automatically. To save the result somewhere durable, the human can specify an explicit proposal and destination: `prop-review <absolute-path-to-proposal.txt> <absolute-path-to-result.txt>`; do not silently persist proposals or results elsewhere. The CLI needs the human's terminal; do not run it from a non-interactive agent shell or answer on the human's behalf. Stop after handing off the review; do not read or report its result in this skill. For a later request to bring results into chat, use `prop-review-ingest`.
4. When the human asks to identify additional open decisions from a reviewed discussion, ask them to run `prop-review clarify` in the repository. It lists root requests/issue titles for human selection, checks the selected review chain, and generates a new linked proposal only when the engine finds additional questions. The human reviews that proposal; no approval implies implementation. Old roots without a saved request/title cannot be clarified. Only when explicitly requested to revise, ask the human to run `prop-review revise` (using the selected engine): it uses the only reviewed proposal with comments and no child revision, or lists eligible proposals for the human to select when several exist (newest modification time, then path). The human can also run `prop-review revise <proposal.txt>` with a relative or absolute path in the same repository to select one directly; missing or mismatched adjacent results fail without falling back to another. It holistically reconstructs the proposal from the original request and full review history, including all comments, rather than replacing items positionally. Retain approved decisions as constraints while allowing their wording and structure to change; unconfirmed items may also change. Items may be merged, split, added, dropped, or reordered. All generated items must have empty `Approval/Comment:` fields and are unapproved; earlier approvals remain historically valid but do not approve the new items. Semantic consistency with approved decisions is not mechanically proven and requires human review. It writes `parent.txt` containing the previous `review.*` directory name and `revision.txt` containing exactly `restructure\n` (a trailing newline) beside the new proposal. `revision.txt` and `followup.txt` (exact content `followup\n`) are mutually exclusive, and neither marker is allowed on a root proposal. Legacy revisions with neither marker retain positional validation: one item per prior non-approved item in order, with unconfirmed text unchanged. Revision does not automatically open review or start implementation. Results saved only to a custom path cannot be used by `revise`. Do not read the result in this skill.

Approval applies only to the specific item. An empty answer is not approval. Never start implementation, convert to zintent approval, or mutate Spec Kit artifacts solely because an item says `Approved`; wait for an explicit human request. If `prop-review` is unavailable, say so and provide the two-line template for manual review instead.
